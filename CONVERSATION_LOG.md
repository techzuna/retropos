### 2026-08-12 — Live on the shared host: login works
- **Context:** `/loop fix this issue, deploy and test the url with login` — iterate until sign-in works at https://restroreserve.amoknepal.com.
- **The blocker, finally pinned down:** `better-sqlite3` could not load, for two independent reasons that between them close every normal route on this host. It publishes **no prebuild for Node 20's ABI (115) at all**, so npm falls through to a source build — and the plan has no compiler, so nothing was produced ("Could not locate the bindings file"). Node 22 does have a prebuild, but it links against **glibc 2.29+** while CloudLinux 7 ships **2.17**, so it installs and then refuses to load. Prebuilt: too new. Compile: impossible.
- **Fix — ship a binary built for the host.** CI compiles `better_sqlite3.node` inside `manylinux2014` (which *is* CentOS 7, glibc 2.17) for both ABI 115 and 127, and `scripts/install-native.js` copies the matching one into the installed package from `server.js` at boot. Because a deploy already touches `tmp/restart.txt`, a release now repairs the driver by itself with nobody in the hosting panel. Verified: the emitted binary needs only `GLIBC_2.14`.
  - Node 18+ official builds require glibc 2.28 and cannot even *start* inside that container. Node 16 (the last that runs on 2.17) drives the build; `node-gyp --target` fetches headers for the real target, so the binary's ABI is unrelated to the Node executing the build.
  - Removed the earlier `.npmrc build_from_source=true` and the `postinstall` rebuild: on a host with no compiler they turn a working `npm install` into a failed one, which is how it ended up with no binary at all.
- **What made the loop possible:** `GET /api/health` probes the driver, WebAssembly and the database independently and returns coarse fault codes (`native-binding-missing`, `database-file-missing`, `schema-missing`…) with no token needed. Before it, every diagnosis needed someone at the panel pasting `stderr.log`; after it, each iteration was a deploy and a curl. It also settled the WASM/LVE worry — `wasm: ok`, so the `--wasm-enforce-bounds-checks` flag in `server.js` did its job.
- **Verified live:** `/api/health` all-ok; wrong password 401 and correct password 200 with a session cookie; owner reaches `/api/users` (200) while a PIN-switched staff member is refused (403); table board serves 9 tables; plus a browser pass confirming owner login, the board rendering, staff PIN sign-in, and Admin hidden from staff.
- **Left over:** the live database still has open orders from earlier testing (~12 days idle on C1, C2, T2, T3) — cancel them from the board. The seeded owner password is still `owner1234` and is public in the repo; change it before real service.

### 2026-08-11 — Automated cPanel deploys, and the symlink trap that would have broken every one
- **Context:** Owner asked whether this could go on Vercel, then supplied a GitHub Actions FTPS workflow from another project as the pattern to follow. Vercel was audited and rejected — SQLite on a read-only serverless filesystem, uploads and backups on disk, an in-process scheduler, an in-memory rate limiter: the build goes green and the till loses every order. cPanel + Passenger is the fit, and `server.js` from 2026-08-05 already targets it.
- **Decisions and findings:**
  - **Turbopack builds are not portable, and this would have shipped broken.** Turbopack resolves native packages through content-hashed *symlinks* under `.next/node_modules` (`better-sqlite3-90e2652d… → ../../node_modules/better-sqlite3`), and FTP cannot carry a symlink. Proved end to end: assembled a release, installed dependencies fresh the way the panel's *Run NPM Install* does, booted — `Cannot find module 'better-sqlite3-90e2652d1716b047'`, every route 500. `serverExternalPackages` fixed better-sqlite3 but not `@prisma/client`, whose alias sits a level deeper. `next build --webpack` emits no `.next/node_modules` at all: boots clean, and the payload falls from 22 MB/860 files to **6 MB/373**. `npm run build` now passes `--webpack` so CI and the by-hand path in DEPLOY.md produce the same portable build; `next dev` still uses Turbopack.
  - `.next/node_modules` reads as 0 B after a build because its entries are symlinks — `du` sees nothing, `cp -r` dereferences and copies ~100 MB of the build machine's binaries. Both readings mislead, in opposite directions.
  - The release tree is an **allow-list**, not an exclude-list: one forgotten exclusion would upload a developer's `data/` over the restaurant's live database.
  - Added a **migration guard**. cPanel has no shell, so `prisma migrate deploy` cannot touch the live `data/app.db`; the workflow fails when a push changes `prisma/migrations`, prints the offline swap procedure, and offers a `workflow_dispatch` input to acknowledge it was done.
  - `package.json`'s build script was missing `prisma generate`, so a fresh clone failed to build **on any host** — including DEPLOY.md's own VPS recipes. Verified against a clean checkout before and after.
  - The build needs no environment variables at all (every route is `force-dynamic`, so nothing prerenders against the database): `DATABASE_URL`, `SESSION_SECRET` and `APP_URL` are runtime-only.
- **Changes:** new `.github/workflows/deploy.yml` — 13 steps: config and FTP-path checks (including a refusal to deploy inside `public_html`, where the backup JSONs would be downloadable), migration guard, typecheck/lint/test, portable build, allow-list assembly with runtime deps pinned to what the build compiled against, a refusal to ship `data/`/`.env`/`*.db`/`*.node`, FTPS upload with `dangerous-clean-slate: false`, and a summary carrying the panel steps and a smoke test. Also `next.config.ts` gained `serverExternalPackages`; `package.json` gained `typecheck` and the portable `build`; DEPLOY.md documents the automated flow and the symlink finding.
- **Verified:** 83 tests, lint, typecheck, a portable build with zero symlinks, and a full release → fresh `npm install` → boot → `/login` 200, `/signin` 307, `/api/auth/session` 403.
- **Next:** owner sets the three secrets and two variables and does the one-time cPanel app setup; *Run NPM Install* stays a manual panel button after any dependency change.

### 2026-08-05 — cPanel deployment path: shipped `server.js`, verified the scheduler survives it
- **Context:** Owner clarified again — the shared host is **cPanel access**, not just FTP. That is the escape hatch flagged last session, so the answer flips from "impossible" to "possible, with a specific procedure and a real ongoing cost".
- **Read the bundled Next docs first**, per AGENTS.md: `node_modules/next/dist/docs/01-app/02-guides/custom-server.md`. Passenger runs a *file*, not an npm script, so `npm run start` is unusable there and a custom server is required.
- **New `server.js`** — the minimal documented Next custom server, ~20 lines. Deliberately **CommonJS**: package.json has no `"type": "module"`, and Passenger's shim hooks CJS, so `require` is a compatibility decision rather than a style lapse. ESLint's `no-require-imports` is switched off for that one file via a scoped override in `eslint.config.mjs` with the reason inline, rather than an inline disable. `npm run dev` / `npm run start` are untouched, so LAN and VPS deployments ignore the file entirely. Added `migrate` and `start:passenger` scripts so cPanel's "Run JS script" has named targets.
- **Verified locally against a production build** on port 3212: every page and API route 200, 404 boundary returns a real 404, no dev chunks. Passenger itself can't be tested from here and the doc says so.
- **The check that mattered most:** does `instrumentation.ts` — and therefore the scheduled-backup timer — still run under a custom server, or do automatic backups silently die? **It runs**, proved by `[backup] wrote 1 scheduled backup(s)` in the log after a clean boot with `lastBackupAt = null`.
- **My first attempt at that test was invalid and I nearly reported the opposite.** I set `lastBackupAt = null` *after* the server had already booted, but the scheduler's first tick is a one-shot `setTimeout(60s)` and the following one is hourly — so 70 seconds of waiting proved nothing. Re-ran with the flag set *before* a fresh boot. Test backup file removed afterwards.
- **The procedure's key trick, documented:** build `.next` **locally** (shared plans cap RAM and `next build` is memory-hungry) but install `node_modules` **on the host** via the panel's Run NPM Install — because `better-sqlite3` is platform-specific and the local copy is `Mach-O arm64`. Also: upload a locally-migrated `data/app.db`, since migrations can't run on the host.
- **The honest ongoing cost, stated plainly in DEPLOY:** every future schema change becomes a manual offline database swap — take `app.db` down by File Manager, migrate locally, upload during a closed period. And four go/no-go panel checks, of which "can it be pinned to one process" is the one that quietly bites (duplicate backups, PIN limit multiplied per worker).
- **Changes:** new `server.js`; `eslint.config.mjs` override; two package.json scripts; DEPLOY.md gained "cPanel-only hosting (no shell) — the workable path" and the FTP section now points at it instead of hedging. All 9 anchors valid. 83 tests, `tsc`, ESLint, production build and the scroll guard clean.

### 2026-07-31 — FTP-only hosting ruled out, with the evidence
- **Context:** Owner clarified the shared server is **FTP access only** — no shell, no control-panel detail given.
- **Answer: it cannot run there**, and I checked rather than asserted:
  - **FTP moves files; it cannot start a process.** Next.js serves from a live `next start`; an FTP upload leaves files with nothing executing them. A PHP/static host has no Node runtime to hand a request to.
  - **The DB driver is platform-locked.** `file node_modules/better-sqlite3/build/Release/better_sqlite3.node` → `Mach-O 64-bit arm64`. That is the dev Mac's binary; it cannot load on a Linux host, and producing a matching one needs a shell to compile on.
  - Consequences of the same root: `prisma migrate deploy` can never run (schema frozen), and the in-process backup scheduler never starts (no automatic backups).
  - **Pre-building locally doesn't rescue it:** ~22 MB of build output *plus* 844 MB of `node_modules` across **31,733 files** over FTP, and it still ends with a platform-wrong binary and nothing running it.
- **Measured, and corrected myself mid-way:** `.next` is 2.7 GB, but 2.7 GB of that is `.next/dev` — dev-server scratch, not part of a release. The actual production build is `.next/server` (20 MB) + `.next/static` + `.next/build` ≈ **22 MB**. I nearly quoted the 2.7 GB figure, which would have been badly misleading.
- **The one escape hatch worth checking** before writing the host off: many shared plans expose a **"Setup Node.js App"** panel (cPanel/Plesk + Passenger) — not FTP, but no SSH needed. Documented the four things to confirm (Node 20+, settable env vars, an NPM-install step that survives `better-sqlite3`, and the ability to pin to one worker) plus the fact that Passenger wants an entry file rather than `npm run start`.
- **Recommended instead:** mini-PC in the restaurant (the design intent — service survives an internet outage), or the cheapest VPS with a subdomain pointed at it, keeping the FTP host for the public website. Both need roughly the plan's own budget.
- **Changes:** new "FTP-only hosting — this cannot work" section in DEPLOY.md. All 8 anchor links verified. No code changed.

### 2026-07-31 — Shared-server release runbook; corrected a wrong claim in DEPLOY.md
- **Context:** Owner asked how to *release* on a shared server (the previous session covered how to stand one up, not how to ship updates to it).
- **Error corrected in my own doc:** yesterday's advisories section claimed the ESLint chain is "never installed on a server built with `npm ci --omit=dev`". **That is wrong — this app cannot build, migrate or seed without devDependencies:** `tailwindcss` + `@tailwindcss/postcss` are referenced by `postcss.config.mjs`, `typescript`/`@types/*` are needed by `next build`, `prisma.config.ts` opens with `import "dotenv/config"` so even `prisma migrate deploy` needs `dotenv`, and the seed runs through `tsx`. So the dev tree *is* on the server; the accurate statement is that none of it is ever *executed* in the request path. Documented as a table of which command needs which devDependency, since `--omit=dev` looks like obvious hardening and breaks three things at once.
- **New "Releasing to a shared server" runbook**, with the parts that differ from the LAN `git pull && build && restart`:
  - **Back up before migrating**, and take a raw `cp -a` of the data directory as well as the JSON — the raw snapshot is the one that survives a bad migration, because migrations are forward-only.
  - **Migrate before build, and know what it costs**: `prisma migrate deploy` changes the schema while the *old* build is still serving, so for a few seconds the running code sees a newer schema than it was compiled against. Safe for additive migrations only; a rename or drop needs the service stopped first. Stated as a rule rather than left implicit.
  - **`next build` gets OOM-killed on 512 MB–1 GB VPS tiers.** Add swap or build elsewhere; a half-dead build leaves `.next` in a state the old process may still be serving from.
  - **Restart drops in-flight requests** — recoverable (the client shows "Can't reach the till" and all three screens re-poll within 15s), but release between services.
  - Run the post-deploy checks against the **public URL**, not localhost: TLS and the `Secure` cookie are the two things only the real URL exercises, and a wrong `APP_URL` presents exactly as "staff can't sign in".
  - Rollback: code rolls back, schema does not — hence step 0.
- **Also fixed the document's internal contradictions**, which had accumulated when I appended the shared-server sections above the existing ones: two unlabelled first-deploy recipes (now "First release: VPS…" vs "First release (outlet box on the LAN)", cross-referenced), `npm install` vs `npm ci` (now `ci` everywhere — the lockfile is committed and a release should install exactly what was tested), Prerequisites still saying a bare "Node.js 20+", and an Environments table with no shared-server row.
- **Verified:** all 7 in-document anchor links resolve (one was broken by a heading rename and is fixed), and every repo path referenced in the doc exists. No code changed this session.

### 2026-07-30 — Deployment guidance for a shared server; production path verified
- **Context:** Owner asked how to deploy on a shared server. DEPLOY.md covered a mini-PC on the LAN and mentioned "a small VPS" in one line with no detail — exactly the gap.
- **Findings first, before writing anything:**
  - **"Shared server" has three meanings** and only two work: a VPS shared by several outlets (already supported — one app, one DB, tenancy scoping separates them), a VPS shared with the restaurant's other sites (fine behind a reverse proxy on a subdomain), and cPanel-style shared hosting (usually fails).
  - **The app is single-process-only today**, for three independent reasons worth writing down: the rate limiter is in-memory (two workers = double the PIN-attempt budget), the backup scheduler is in-process (two workers = duplicate backups), and SQLite has one writer. Any multi-worker host — Passenger's default, PM2 cluster — breaks all three. Documented with the prerequisites for ever going multi-process.
  - **Checked rather than assumed:** I expected `busy_timeout=0` and was about to add WAL to fix a phantom bug. The adapter already sets **5000ms**, so concurrent readers wait rather than fail. Journal mode is `delete`, which is fine single-process. No code change made; WAL is listed only as a prerequisite for multi-process.
  - `APP_URL` must be `https://` on an internet-facing host — the session cookie's `Secure` flag derives from it. `TRUSTED_PROXY=1` only when a proxy really is in front, since otherwise a client can forge `x-forwarded-for` and dodge throttling entirely.
- **Verified the production path end to end for the first time** (everything so far had only ever run `next dev`): `npm run build` → `PORT=3210 npm run start` → all six APIs and four gated pages 200, a real 404 from the error page, and `POST /api/backups` wrote a backup file — which proves the native module's write path under `NODE_ENV=production`.
- **Dependency audit, since this is about exposing the app to a network:** 12 high-severity advisories, **none in the request-handling path**. Nine are the ESLint chain (dev-only, absent under `npm ci --omit=dev`); `postcss` is build-time and only ever sees our own CSS; `sharp` is reachable only via Next's image optimizer, and `next/image` is imported nowhere — dish photos are plain `<img>` off our own disk. Recorded in DEPLOY with the advice to run `npm audit fix` (never `--force`) before an internet-facing deploy.
- **Changes:** DEPLOY.md gained "What any server must provide" (hard requirements table + the run-one-process rationale), a "Shared server" section (the three meanings, a full VPS + systemd + nginx + TLS recipe, and three go/no-go checks for cPanel hosting), and a dependency-advisories subsection; `package.json` gained `engines: node >=20`, so a host with the wrong Node fails loudly instead of at native-module load.
- **Note:** an unescaped backtick in one of my `echo` strings executed `npm ci` for real, reinstalling `node_modules` mid-session. Confirmed no damage — dev and prod servers still 200, native module still loads, 83 tests, `tsc`, ESLint all clean. Also surfaced something useful: a transitive Prisma package declares `node >=22`, so DEPLOY now says 20 minimum / 22 LTS preferred rather than a bare "Node 20+".
- **Next:** owner to say which kind of shared server they have. If it is cPanel-style, work through the three checks before anything else — and note that hosting remotely inverts the local-first premise (an internet outage stops the till), which is the same trade flagged in the hosted-platform design.

### 2026-07-30 — Cross-device sync: the bookings and order screens weren't polling
- **Context:** Staff question from the owner: sitting on `/pos` without refreshing, while another staff member books that table — does the screen sync?
- **Measured first, with two browser contexts:** the **board already did** — waiter A's `/pos` picked up waiter B's booking in ~14s with zero interaction, via `AutoRefresh` at 15s. But `/pos/reservations` was **still stale after 25s**, and the order screen never polled either. So the honest answer was "the board yes, the other two no".
- **Decisions:**
  - Mounted `AutoRefresh` on the bookings screen. Two hosts can be taking calls at once, which makes it arguably the *more* likely collision — and it was the one screen that never updated. Paused while a manager edits service times, same reasoning as the floor plan.
  - The order screen needed a different fix: `AutoRefresh` would have been useless there, because the lines live in `items`, client state seeded from props, and `router.refresh()` cannot reach `useState` once mounted — the server tree would refresh while the visible lines silently didn't. It now polls `/api/orders/[id]` directly and sets `items` from the response. Paused while our own write is in flight, since that mutation refetches anyway and a poll landing mid-flight would briefly redraw the pre-write state.
  - **Kept polling rather than moving to SSE.** One Node process on a LAN box, a handful of tablets, 15s worst case: no connection lifecycle, no reconnect logic, and a Wi-Fi blip is absorbed by simply succeeding next time. Recorded in DESIGN, with SSE named as the upgrade if sub-second ever matters.
  - Worth stating explicitly because it's the actual guarantee: **correctness never depended on freshness**. A stale screen can only offer an action the server then refuses — `TABLE_OCCUPIED` on a double-seat, `TABLE_DOUBLE_BOOKED` on a clashing booking. The poll is convenience; those guards are the safety.
- **Changes:** `AutoRefresh` mounted in `reservation-manager.tsx`; a polling effect in `order-screen.tsx`. Docs: AGENTS a sync convention, DESIGN a note on the mechanism and why not SSE.
- **Verified with two independent browser contexts, unique guest names per run:** A untouched on the board synced in ~14s; A untouched on bookings synced in ~15s (was never); A untouched on the order screen saw B's 3× line appear in ~14s, with the pinned settle total following to NPR 1,350. Test data cleaned up after. 83 Vitest tests, `tsc`, ESLint, build and the horizontal-scroll guard all clean.
- **Note:** two of my own sync assertions were initially false positives — the first run reused guest names already in the database, and "Chicken Momos" matched a *menu row* rather than an order line. Re-tested with per-run unique names and the unambiguous "Nothing ordered yet" signal.

### 2026-07-29 — Error UX: real failure screens, and naming a dropped connection
- **Context:** Owner: "make error page UX better." The app had **no** `not-found.tsx`, `error.tsx` or `global-error.tsx`, so a stale table link got Next's bare 404 and a thrown render got "Application error: a server-side exception has occurred" — on a tablet, mid-service, with no way back.
- **Decisions:**
  - Three boundaries sharing one `components/ErrorScreen.tsx`, written for the person who actually meets them: a waiter holding a tablet who will not read a stack trace and needs one obvious way back to work. Every screen has a link to the table board.
  - **`not-found.tsx`** — in a POS the honest cause is almost never "wrong URL", it's a link gone stale because the order was settled or the table retired. The copy says that. `404` tells a waiter nothing.
  - **`error.tsx`** — "Try again" first, calling `reset()`, because the likely causes on a LAN box are transient (server restarting, SQLite briefly locked, a dropped request) and a reload would cost the staff their place. Deliberately does **not** print `error.message`: production redacts server errors, so it would read as a placeholder. Shows `error.digest` as "a reference for the owner" instead — the thread back to the server log.
  - **`global-error.tsx`** — the root layout itself failing, which `error.tsx` can't catch. Brings its own `<html>`, imports the palette, and deliberately skips the web fonts: a page whose whole job is rendering when nothing else could shouldn't add another thing that can fail. System fonts are the trade.
  - **Data reassurance is conditional.** The crash screens say orders and bills are safe on the server, because that's the first thing a waiter fears. The 404 does *not* — raising it there invents an alarm nobody had (`reassure={false}`).
  - **New `lib/fetch-error.ts`**: a rejected `fetch` (device never reached the server) now reads "Can't reach the till — check this device is on the restaurant's network", separately from a response that arrived and said no. The first is the common failure on a restaurant LAN and the fix is in the room; collapsing both into "that didn't go through" told staff nothing actionable.
- **Bug found while wiring that up:** the order screen's `mutate()` tested `if (res && !res.ok)`, so a **rejected fetch showed no error at all** — a dropped connection while adding an item, changing a quantity or editing a note looked like nothing happened. Now handled. `settle` and `cancelOrder` had the same generic text and now use the shared helper too.
- **Changes:** new `ErrorScreen`, `not-found.tsx`, `error.tsx`, `global-error.tsx`, `lib/fetch-error.ts`; error handling in `table-board`, `reservation-manager`, `menu-manager`, `admin-panel`, `order-screen`, `seat-form` routed through it. Docs: PRD §7 gained a Failure-UX requirement, DESIGN two UI/UX notes, AGENTS two conventions.
- **Verified in the browser:** `/pos/tables/gone` returns a real **404** with our copy at 375px and 900px, reassurance panel correctly hidden, no overflow; an unknown URL uses the same page; a deliberately-throwing probe route was caught by `error.tsx` showing Try again / Back to tables plus the digest, then the probe was deleted; aborting every `/api/**` request produced the network message rather than a generic one. Also confirmed auth still precedes not-found — signed out, `/pos/tables/gone` redirects to `/login` rather than 404ing. 83 Vitest tests, `tsc`, ESLint, production build and the horizontal-scroll guard all clean.
- **Not verified:** `global-error.tsx` — triggering it needs the root layout itself to throw, which I could only force by breaking the app. It compiles and is wired; the path is untested by design.

### 2026-07-28 — Hosted multi-tenant platform designed (design only, nothing built)
- **Context:** Owner asked how a "master admin / super admin" would handle multiple organizations, then whether that needs a portal. The honest answer to the first: it can't — `owner` is the top of `ROLES` and every `src/lib` function pins queries to `ctx.orgId`, so no actor exists above a tenant and organizations are only created by the seed or a backup restore. Offered three readings (vendor control plane over self-hosted installs / hosted SaaS / one business with several brands); owner chose **hosted SaaS** — customers sign up and run on our server, no box on their premises.
- **Decisions** (all recorded as a proposal in DESIGN.md, none implemented):
  - **One SQLite file per organization**, not one shared file relying on the existing `organizationId` columns. Deciding reason: SQLite serializes writes per file, so a shared file makes one busy restaurant's settles contend with every other restaurant's till. File-per-tenant also makes isolation physical, makes per-tenant backup/restore a file operation, and fixes the globally-`@unique` `User.email` that would collide across tenants. Existing org/outlet scoping stays untouched and becomes defence-in-depth.
  - **Tenant resolved from the request host**, never from the cookie; the cookie's `orgId` is then asserted equal to the host-resolved tenant. Noted that the session cookie's *absence* of a `domain` attribute is currently incidental but becomes load-bearing — setting `domain: ".restroreserve.app"` would make one tenant's cookie valid at every other tenant.
  - **Super admin lives in a separate control-plane database, deliberately NOT as a fourth entry in `ROLES`** — that array is an ordered ladder feeding `roleAtLeast()`, so a platform-wide role at its top would turn every `requireRole()` into a possible cross-tenant hole. Reaching tenant data requires a reason-bearing, minutes-long, audit-logged impersonation grant that mints an ordinary tenant session flagged `impersonatedBy`, with a banner the customer can see.
  - **`db.ts` stops being a singleton** — `tenantDb()` + `controlDb()`, client carried as `ctx.db` alongside the tenancy ids it already carries. The enforcing move: **delete the `prisma` export** so `import { prisma }` no longer compiles and nothing can silently fall back to a default database. Chose explicit `ctx.db` over `AsyncLocalStorage` because hiding which database a write lands in is exactly the wrong thing to hide.
  - Provisioning as a resumable state machine on `Tenant.status` (`pending → migrating → seeding → ready`, plus `failed`/`suspended`), since signup creates a file, migrates it, and seeds an owner — a crash between any two must be recoverable.
  - Fleet migrations are the main ongoing cost: `migrate:tenants` fan-out, per-tenant `schemaVersion`, refusal to serve a tenant that is behind, and two-phase deploys — which forces backward-compatible migrations (additive only, no renames/drops in the same release).
  - Control plane is a **separate service/repo**: billing, signup site, admin console, provisioner, DNS/TLS all stay out of this repo so the POS cannot reach the tenant registry.
  - Flagged the deltas for uploads (per-org directories), backups (off-box upload becomes mandatory, not PRD §6 nice-to-have), the backup scheduler (iterate the registry, bounded concurrency), and rate limiting (per-process `Map` is simply wrong with >1 instance → sticky routing or Redis).
  - Exit ramp noted: the `ctx.db` seam makes Postgres-schema-per-tenant an adapter change rather than a domain rewrite. Not to be built until tenant count or an uptime commitment demands it.
- **Raised, not decided:** hosted **deletes the local-first guarantee** the current design is built around — an ISP outage stops service at the till. That contradicts PRD §8 ("No cloud multi-region hosting — this is a self-hosted, local-first system"), and promotes offline-first PWA from §6 nice-to-have to near-prerequisite, which is substantial work because settle-time freezing and one-open-order-per-table both assume a single authoritative writer. Four open questions left for the owner in DESIGN.md (self-hosted kept or replaced; offline-first before launch or documented limitation; data controller and deletion commitment; region/residency). PRD.md deliberately **not** edited — changing §7/§8 is the owner's call.
